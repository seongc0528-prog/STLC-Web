# STLC 홈페이지 프로젝트 — 2026-09-10 작업 기록

## 1. 이 세션의 목표

Flutter 앱(`my_app1`)에는 있었지만 웹 뼈대에는 없던 **데일리 말씀 정시 푸시 알림**을 구현.
관리자(STLC_Admin)에는 "인스턴트 메시지 작성 → 전체 발송"만 있었고, 주기적인 예약 발송
기능이 없었다.

### 기존(Flutter) 방식과 달라진 점

| | 기존 Flutter 앱 | 이번 웹 구현 |
|---|---|---|
| 말씀 저장 위치 | 앱에 내장된 `assets/daily_messages.json` (200건) | Supabase `daily_verses` 테이블 |
| 푸시 내용 | "알림이 왔다"는 빈 메시지만 발송 | **말씀 본문을 담아서** 발송 |
| 말씀 선택 | 앱이 날짜로 인덱스 계산 후 화면 표시 | 서버가 같은 규칙으로 계산 |
| 말씀 수정 | 앱 재배포 필요 | 관리자 화면에서 즉시 수정 |
| 발송 시각 | 앱의 local notification | 서버 크론 + 관리자에서 시각 변경 가능 |

날짜 → 말씀 매핑 규칙은 앱과 **동일하게 유지**: `(2025-01-01 부터 경과일) % 전체 건수`.
검증: 2026-09-10 = 617일 경과 → `617 % 200 = 17`(0-based) → `order_no 18` (앱과 일치).

## 2. 구현 내용

### DB — `supabase/migrations/0007_daily_verses_scheduled_push.sql`

- **`daily_verses`** — 말씀/명언 원본. `order_no`(unique), `type`(bible/quote), `text_kr`,
  `text_en`, `is_active`. RLS: 비로그인도 읽기 가능(오늘의 말씀 페이지), 쓰기는 관리자만.
- **`scheduled_pushes`** — 주기적 예약 발송 정의. `kind`가 `daily_verse`면 본문을 그날의
  말씀으로 자동 생성, `text`면 등록된 고정 문구를 반복 발송. `send_time` + `timezone` +
  `days_of_week`(빈 값이면 매일) + `last_sent_on`.
- **`daily_verse_for(date)`** — 날짜 → 말씀 계산을 DB 한 곳에만 두고, 웹 페이지와 발송
  함수가 모두 이 함수를 호출한다(계산 규칙이 두 군데로 갈라지지 않도록). SECURITY DEFINER
  + anon/authenticated EXECUTE 권한.
- **`push_logs`** 확장 — `source`(manual/scheduled), `schedule_id` 추가해 수동 발송과
  예약 발송을 구분.
- 기본 예약 1건 자동 생성: 시드니 시간 매일 07:00 "오늘의 말씀".
- 말씀 200건 시드 포함 (아래 4번 참조).

### 발송 — `supabase/functions/run-scheduled-push/index.ts`

호출 경로 두 가지:
1. **pg_cron → pg_net** 이 5분마다 호출 (헤더 `x-cron-secret`)
2. **관리자 "지금 발송"** (관리자 JWT + `{scheduleId, force:true}`)

설계상 신경 쓴 부분:
- 크론은 5분마다 깨우기만 하고, "지금 보낼 게 있는지"는 함수가 판단한다. 예약마다
  타임존/요일이 다를 수 있어 크론 표현식으로는 표현할 수 없기 때문.
- **하루 한 번 보장**: 발송 전에 `last_sent_on`을 조건부 UPDATE로 선점한다. 크론 실행이
  겹쳐도 한 번만 나가고, 발송이 실패하면 선점을 되돌려 다음 크론에서 재시도한다.
- **뒤늦은 발송 차단**: 크론이 멈췄다 살아나도 예정 시각 +120분(`CATCH_UP_MINUTES`)이
  지나면 보내지 않는다. 새벽에 알림이 울리는 사고를 막기 위한 것.
- `force` 발송은 `last_sent_on`을 건드리지 않아 정규 발송에 영향이 없다.

### 크론 — `supabase/cron/0007_schedule_pushes.sql`

`pg_cron` + `pg_net`으로 5분마다 Edge Function 호출. `__CRON_SECRET__` 자리를 실제
시크릿으로 바꿔 SQL Editor에서 1회 실행. **아직 실행하지 않음** (아래 5번 참조).

### 관리자 (STLC_Admin)

- **`/scheduled-push`** (`ScheduledPushPage.tsx`) — 예약 CRUD, 요일 토글 UI,
  오늘 나갈 말씀 미리보기, "지금 발송" 테스트 버튼.
- **`/daily-verses`** (`DailyVersesPage.tsx`) — 말씀 원본 CRUD (`CrudPage` 재사용).
- `useCrud` / `CrudPage`에 `ascending` 옵션 추가 (말씀은 순번 오름차순으로 봐야 해서).

### 홈페이지 (STLC_Web)

- **`/daily-verse`** — 오늘의 말씀 페이지. 시드니 기준 날짜로 조회하므로 서버가 어느
  타임존에 떠 있든 푸시와 같은 말씀이 나온다. 비로그인 열람 가능.
- `sw.js` 개선 — 푸시 페이로드의 `url`로 이동하고, 이미 열려 있는 창이 있으면 새 창을
  띄우지 않고 그 창을 재사용한다.
- `nav.ts` 커뮤니티 섹션에 "오늘의 말씀" 추가.

## 4. 말씀 콘텐츠 검수 (200건 전수)

Flutter 앱의 `daily_messages.json`을 그대로 옮기려다 199번 출처가 이상해서
("주님의 은혜는 매일 새롭다. — 제러마이어 애" / "Jeremiah Lamentations" = 예레미야애가를
사람 이름으로 표기) 200건을 전부 검수했고, 오류가 상당수 발견되어 수정했다.

### 발견된 문제

1. **중복 20건** — 81~97, 105, 152/157, 184, 188, 192, 197, 200번 구간이 앞부분을 짧게
   줄여 재탕한 것. 200일 주기라 같은 말씀이 몇 주 간격으로 두 번 나올 상황이었다.
2. **한글/영문이 아예 다른 내용** — 30번(시 121:5 vs 121:7), 55번(본회퍼 인용문).
3. **성경 본문 각색** — 65번(전도서 8:4는 *인간 왕*의 권세를 말하는 구절인데 하나님
   말씀처럼 각색), 149번(잠 23:26의 화자가 뒤집힘), 64번(시 37:6이 개역개정과 다름),
   171번·199번(성경 구절인데 `quote`로 분류하고 인물 인용처럼 표기).
4. **출처 오기** — 194번 George Barnard → **George Bennard**(「갈보리산 위에」 작사자),
   53번(웨슬리 귀속이 불확실한 문구), 141번(어느 클레멘트인지 불명).
5. **오타** — 168번 "향상" → "항상".

### 수정 방침

- 중복 20슬롯은 **끄지 않고 새 말씀으로 교체**해 200일 주기를 유지했다.
  - 성경 12건: 원본이 시편에 심하게 쏠려 있어(140건 중 60건 이상) 의도적으로 선지서·
    서신서를 넣었다 — 렘 29:11, 사 43:2, 마 7:7, 요 8:32, 롬 12:12, 빌 4:6, 갈 5:22,
    습 3:17, 엡 6:10, 히 11:1, 시 51:10, 미 6:8.
  - 명언 8건: **출전이 분명한 인용문으로만** 교체하고 책/기도문/문답 이름을 함께 표기
    (본회퍼 『나를 따르라』, 어거스틴 『고백록』, 아빌라의 테레사, 웨스트민스터 소요리문답
    제1문, 토마스 아 켐피스 『그리스도를 본받아』, 짐 엘리엇, 엘리자베스 엘리엇, 존 뉴턴).
- 최종: **200건 유지, 중복 0건**, bible 140 / quote 60.

### 남겨둔 문제 (다음에)

71~114, 135~174 구간의 명언 상당수가 여전히 **"출전이 확인되지 않는 일반적인 문구 +
유명인 이름"** 형태다 (예: 72번 조지 뮬러, 108번 빌리 그레이엄, 114번 제리 시처,
166번 스미스 위글스워스). 짧고 평이한 문장이라 원출처 특정이 어렵다. 잘못된 귀속을
없애려면 근거 있는 인용문으로 교체하거나 저자 표기를 빼야 한다.

## 5. 실제로 완료한 것 / 남은 것

### 완료

- 마이그레이션 0007을 **운영 DB에 적용 완료** (`supabase db push`).
  - 이때 0001~0006이 SQL Editor에서 수동 실행돼 마이그레이션 이력이 비어 있었기 때문에,
    먼저 `supabase migration repair --status applied 0001 ... 0006`으로 이력을 맞춘 뒤
    push해서 0007만 나가도록 했다. **앞으로는 `supabase db push`로 관리 가능.**
  - 검증: `daily_verses` 200건, `scheduled_pushes` 1건, `daily_verse_for('2026-09-10')`
    → order_no 18 (앱과 일치), anon RPC 호출 가능, anon의 `scheduled_pushes` 조회는
    RLS로 차단됨(빈 배열).

### 남은 것 (운영자 작업 필요)

1. `supabase functions deploy run-scheduled-push`
2. `supabase secrets set CRON_SECRET=<랜덤 문자열>`
3. `supabase/cron/0007_schedule_pushes.sql`의 `__CRON_SECRET__`을 2번 값으로 치환 후
   SQL Editor에서 실행
4. 관리자 `/scheduled-push`에서 "지금 발송"으로 실제 알림 수신 테스트

**3번까지 끝나야 정시 자동 발송이 동작한다.** 그 전까지는 관리자의 "지금 발송"만 된다.
